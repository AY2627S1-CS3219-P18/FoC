# Sending system notifications from another microservice

Call `POST /chat/send-system-notification` to add a system message to an order
conversation or to a recipient's personal system conversation. Chat Service saves
the message and broadcasts it to connected participants. Order-linked requests
require an existing order conversation. Orderless requests lazily create the
recipient's system conversation without creating an order.

## Address and authentication

| Caller location                         | Base URL with the current Compose defaults                      |
| --------------------------------------- | --------------------------------------------------------------- |
| Container on the shared Compose network | `http://chat-service:3000`                                      |
| Host machine                            | `http://localhost:3005` (or the configured `CHAT_SERVICE_PORT`) |

For other deployments, use that deployment's Chat Service base URL.

Send these headers:

| Header          | Value                                                         |
| --------------- | ------------------------------------------------------------- |
| `Content-Type`  | `application/json`                                            |
| `X-Service-Key` | The shared key matching Chat Service's `CHAT_SERVICE_API_KEY` |

The calling service must load `CHAT_SERVICE_API_KEY` from its `.env` file into
its backend environment and put that value in the `X-Service-Key` request header
for authentication. The value must match the key configured in Chat Service.
`CHAT_SERVICE_API_KEY` is the environment variable name; `X-Service-Key` is the
HTTP header name. Chat Service reads the header, not the caller's `.env` file.

For example, with this placeholder configuration in the calling service's `.env`:

```dotenv
CHAT_SERVICE_API_KEY=<shared-chat-service-key>
```

Send the loaded value as:

```ts
headers: {
  "Content-Type": "application/json",
  "X-Service-Key": process.env.CHAT_SERVICE_API_KEY!,
}
```

Replace the placeholder with the configured shared key. Ensure the environment
variable is loaded before making the request; the snippet assumes it is present.

`X-Service-Name` is not required or checked by this endpoint. Any service with a
valid shared key can call it. A user Bearer token alone cannot authorize this
operation. If `X-Service-Key` is supplied, it takes precedence over Bearer auth;
an invalid key returns 401 even with a valid user token. Keep the key in backend
configuration; do not put it in frontend code or commit its value.

## Request body

```json
{
  "orderId": "0192f0c4-0000-7000-8000-000000000001",
  "messageId": "0192f0c4-0000-7000-8000-000000000002",
  "message": "The order has been created"
}
```

| Field       | Required               | Meaning                                                                                                                            |
| ----------- | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `orderId`   | Yes                    | Order UUID for an order notification, or explicit JSON `null` for an orderless notification. Do not omit this field.               |
| `recipient` | When `orderId` is null | Recipient user UUID. Required for orderless notifications; not used to route order-linked notifications.                           |
| `messageId` | Yes                    | UUID generated by the service sending the notification. Generate it once per notification and reuse the same ID for every retry.   |
| `message`   | Yes                    | Non-empty string containing the complete text to display. Whitespace-only strings are rejected; accepted text is stored unchanged. |

An order-linked notification must already have an ACTIVE order conversation.
The caller does not supply `senderId`, `type`, `metadata` or `conversationId`.

## Orderless notifications

For a notification with no associated order, send explicit `orderId: null` and
supply `recipient` as the user's UUID:

```json
{
  "orderId": null,
  "recipient": "0192f0c4-0000-7000-8000-00000000000a",
  "messageId": "0192f0c4-0000-7000-8000-000000000004",
  "message": "Your scheduled order could not be created."
}
```

The first notification creates an ACTIVE conversation titled `FoC`, with null
orderId and a single recipient participant whose role is null. The unique user
mapping in `system_chats` ensures subsequent notifications reuse that conversation.
Conversation and mapping creation share a transaction; a concurrent duplicate-user
attempt rolls back its new conversation and reuses the winning mapping. Messages
still reference the existing conversations table. No SYSTEM user is added.

An explicitly supplied malformed order UUID returns 400. A valid order UUID
without a conversation returns 404. Neither case falls back to a system chat;
`recipient` does not override an order UUID.

The recipient sees the conversation in their chat list, pinned first by the
frontend, and its messages appear as incoming messages from FoC. Users can read
and mark messages as read, but sending to a system conversation returns 403.
Other users cannot access its details, history or socket room.

Apply the checked-in system-chat migration before using orderless notifications:

```sh
cd chat-service
npm run db:generate
npm run db:deploy
```

### Orderless cURL example

Set `CHAT_SERVICE_URL` to the appropriate base URL above and load
`CHAT_SERVICE_API_KEY` into the environment. Replace the example recipient UUID
with the actual recipient. Generate `MESSAGE_ID` once for this notification:

```sh
MESSAGE_ID=$(uuidgen)

curl --include --request POST \
  "$CHAT_SERVICE_URL/chat/send-system-notification" \
  --header 'Content-Type: application/json' \
  --header "X-Service-Key: $CHAT_SERVICE_API_KEY" \
  --data "{
    \"orderId\": null,
    \"recipient\": \"0192f0c4-0000-7000-8000-00000000000a\",
    \"messageId\": \"$MESSAGE_ID\",
    \"message\": \"Your scheduled order could not be created.\"
  }"
```

Expect 201 for a new message. Repeat the same cURL command without regenerating
`MESSAGE_ID` to test an identical retry: expect 200 and no duplicate message.
A distinct notification uses a new message UUID and reuses the same system chat.

## cURL example

With `CHAT_SERVICE_URL` and `CHAT_SERVICE_API_KEY` supplied through your environment:

```sh
curl --include --request POST \
  "$CHAT_SERVICE_URL/chat/send-system-notification" \

```

The UUIDs above are examples: replace the order ID with an existing order's ID
and use a new message UUID for each distinct notification.

## Node.js / TypeScript request example

This uses the built-in `fetch`, as the existing order-service client does.
`notification` represents an already-created delivery payload. Keep that same
payload if the caller retries the delivery.

```ts
const notification = {
  orderId: "0192f0c4-0000-7000-8000-000000000001",
  messageId: "0192f0c4-0000-7000-8000-000000000002",
  message: "The order has been created",
};

const response = await fetch(
  new URL("/chat/send-system-notification", chatServiceUrl),
  {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "X-Service-Key": chatServiceApiKey,
    },
    body: JSON.stringify(notification),
  },
);

if (response.status !== 200 && response.status !== 201) {
  // Error bodies are not consistently JSON.
  const detail = await response.text();
  throw new Error(`Chat Service returned ${response.status}: ${detail}`);
}

const savedMessage = await response.json();
```

`chatServiceUrl` and `chatServiceApiKey` come from the calling service's backend
configuration. This example performs one request; it does not add a retry policy.

## Responses

Both successful statuses return the message object directly, with no
`success` or `data` wrapper:

```json
{
  "messageId": "0192f0c4-0000-7000-8000-000000000002",
  "conversationId": "0192f0c4-0000-7000-8000-000000000003",
  "senderId": null,
  "type": "SYSTEM",
  "content": "The order has been created",
  "metadata": null,
  "createdAt": "2026-11-08T12:00:00.000Z"
}
```

| HTTP status                 | Meaning                                                                                         |
| --------------------------- | ----------------------------------------------------------------------------------------------- |
| `201 Created`               | A new SYSTEM message was saved.                                                                 |
| `200 OK`                    | An identical notification already exists for this message ID; returns that message.             |
| `400 Bad Request`           | Missing or invalid body fields, invalid UUIDs, or empty/whitespace-only message.                |
| `401 Unauthorized`          | Missing/invalid credentials, including an invalid service key.                                  |
| `403 Forbidden`             | Authenticated using only a valid user Bearer token.                                             |
| `404 Not Found`             | No conversation exists for the order, or the resolved conversation is missing.                  |
| `409 Conflict`              | Conversation is not ACTIVE for a new message, or message ID conflicts with an existing message. |
| `500 Internal Server Error` | An unexpected lookup or persistence failure occurred.                                           |

Controller validation, not-found and conflict responses use plain text
(`Bad Request`, `Not Found`, `Conflict`); the Bearer-only rejection is also plain
text (`Forbidden`). Invalid service keys return JSON
`{"message":"Unauthorized","code":"UNAUTHORIZED"}`. Unexpected controller
errors return JSON `{"message":"Internal server error."}`. Check the HTTP
status before trying to parse an error body as JSON.

## Duplicate handling and retries

The service sending the notification must generate `messageId` as a UUID once
per notification, before the first delivery attempt. Chat Service does not generate
this ID for the caller. Every retry must reuse that same `messageId`, along with
the same `orderId`, the same `recipient` for orderless notifications, and exact
`message` text. Do not generate a new UUID for each
retry.

- An identical retry returns 200 without inserting another message, updating the
  conversation timestamp or broadcasting again.
- Reusing a message ID with different text, a different order, or a different system-chat
  recipient returns 409.
  An ID belonging to a non-system message also conflicts.
- Generating a fresh ID on a retry creates a distinct message if the earlier
  attempt succeeded.
- Existing identical messages are checked before conversation status, so an
  identical retry can return 200 even after that conversation is archived.

The existing [order-service client](../order-service/src/clients/chat.client.ts)
classifies network failures and HTTP 5xx as transient, and other non-success
HTTP responses as permanent. This describes that client; Chat Service does not
schedule retries for callers.

## Persistence and realtime delivery

System conversation creation commits before the message transaction. If message
insertion fails, an empty system conversation may remain; retries reuse it.

For a new notification, message insertion and the conversation's `updatedAt`
change happen in one transaction. After commit, Chat Service emits
`message:sent` with the returned message object to the union of:

- `chat:<conversationId>`;
- `user:<userId>` for each non-revoked conversation participant.

The first saved orderless notification uses the same event to notify the recipient
through their user room, so an open frontend can refresh its conversation list.
No separate conversation-created event is emitted.

A socket belonging to multiple target rooms receives one union broadcast.
The calling microservice only needs the HTTP call for this operation.
A successful HTTP response confirms persistence; it does not acknowledge receipt
by every frontend. Broadcast errors are logged and do not undo the saved message
or change the successful response. Identical retries do not rebroadcast.
